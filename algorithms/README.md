# 核心算法模块

这七个文件是从 3.5 万行的主程序里**剥离出来的算法层**。剥离的标准很简单：不依赖 GUI、不依赖全局状态、能单独 import 就跑。

每个文件都能直接执行：

```bash
python loadgen.py
python spaces.py
python dispatch.py
python finance.py
```

---

## 阅读顺序建议

如果是第一次接触储能测算，按这个顺序看：

```
loadgen.py  →  spaces.py  →  dispatch.py  →  finance.py  →  milp.py
  造数据        算空间         排调度          算钱           求最优
```

`periods.py` 和 `diagnostics.py` 是旁支，需要时再翻。

## periods.py — 分时电价与时段

**解决什么问题**：中国的分时电价把一天切成峰、平、谷若干段，每段电价不同。所有测算的起点是「这一天哪几个小时是峰、哪几个是谷」。

**输入格式的坑**（这是本项目踩过最多次的地方）：系统里同时存在三种时段写法，历史上互相不兼容：

```python
# ① dict 格式 —— 分段计算用的规范格式
[{'start': 8.0, 'end': 11.0, 'type': 'flat'}, ...]

# ② 元组格式 —— 省份电价库里存的格式
[(0, 8, 'valley'), (8, 11, 'flat'), ...]

# ③ 字符串格式 —— 外部导入、配置文件里常见
[('08:00', '11:00', 'flat'), ...]
```

`_normalize_periods()` 负责把三种统一成 ①。**任何外部时段数据进算法层之前都应该先过这一道**，否则会在 `abs(p['start'] - current_end)` 这种数值比较处炸掉。

**核心函数**：

| 函数 | 作用 |
|---|---|
| `_to_hour(v)` | 把 `8` / `"08:00"` / `datetime.time(8,0)` 统一成小时数 float |
| `_normalize_periods(periods)` | 三种格式 → 统一 dict 列表 |
| `_expand_overnight(periods)` | 跨午夜时段拆分（`22:00→06:00` 拆成 `22-24` 和 `0-6`） |
| `_segment_periods(periods)` | 把相邻同类型时段合并成「充电1 / 放电1 / 充电2」这样的连续段 |
| `periods_to_price_series(...)` | 展开成与负荷曲线等长的逐点价格序列 |

**为什么需要分段**：储能不是随时都能充。它只能在谷段充、峰段放，中间隔着平段。`_segment_periods` 把一天切成若干个「连续可充电窗口」和「连续可放电窗口」，后面的空间计算和调度都基于这些窗口。

## spaces.py — 充放电空间

**解决什么问题**：给定一条负荷曲线和时段策略，「这个时段最多能充多少电、最多能放多少电」。

这是整个工具的核心概念。**容量不是拍出来的，是被负荷曲线和电价结构「挤」出来的空间**。

**两种口径**：

| 函数 | 输入 | 适用 |
|---|---|---|
| `compute_daily_spaces(...)` | 原始时段列表 | 快速估算，按天算一个总空间 |
| `compute_segmented_spaces(...)` | 已分段列表 | 精确计算，逐段给出空间，供调度使用 |

**核心逻辑**（以 Mode B 为例）：

- **可充电量** = 谷段内高于「充电功率上限」的负荷空间 + 变压器容量余量
  - 充电不能把负荷推到变压器容量以上 → 受 `rated_power`（变压器容量）约束
  - 充电功率受 PCS 额定功率约束

- **可放电量** = 峰段内负荷本身消耗的量（削峰不能削到负数）
  - 放电是把负荷「挖下来」，挖到 0 为止 → 受当前负荷值约束
  - 同时受 PCS 功率约束

**关键参数**：

- `billing`：基本电费模式。`None` 表示按容量计费，有值表示按需量计费。两种模式下的空间算法不同。
- `mode`：`A` 手动填倍率 / `B` 按比例分担 / `C` 按容量分担。多资产场景下决定每个资产分到多少空间。
- `rated_power`：变压器容量（kW）。传 `None` 表示不限制。
- `ignore_negative`：是否忽略负负荷（光伏倒送场景）。

**一个容易踩的点**：充放电空间是**电网侧口径**，不是电池侧口径。也就是说「可充电量 1000 kWh」指的是从电网取 1000 kWh，进电池要乘充电效率。如果在下游经济模型里又除一次效率，就会重复折算——这个 bug 在本项目里真实存在过，导致套利收益被低估 14%。

## dispatch.py — 三种调度引擎

**解决什么问题**：知道有多少空间之后，具体怎么充、怎么放，才能收益最大。

三种实现，各有适用场景，**故意放在同一个文件里方便对照**：

### 1. `greedy_dispatch_annual(load_kw, pv_kw, ...)` — 贪心

逐时段判断：谷段就充，峰段就放，SOC 到边界就停。

- **优点**：快，全年 8760 点毫秒级
- **缺点**：局部最优，遇到连续峰段可能提前放完
- **用途**：界面预览、快速试算

### 2. `simulate_daily_dispatch(load_array, time_labels, periods, ...)` — 逐日仿真

按天独立仿真，输出完整 SOC 轨迹，能看到每时刻电量。

- **优点**：SOC 轨迹可视化，便于人工判断策略是否合理
- **缺点**：天与天之间不耦合，跨日策略无法表达
- **用途**：方案演示、SOC 曲线出图

### 3. `optimal_dispatch_lp(load_kw, buy_price, sell_price, ...)` — 线性规划

把充放电写成 LP：目标函数是收益最大，约束是 SOC 上下限、功率上限、不能同时充放。

- **优点**：给定容量下的理论最优
- **缺点**：需要 scipy，求解有时间成本；不考虑电池衰减
- **用途**：基准线——如果贪心结果离 LP 很远，说明策略有改进空间

**SOC 口径统一**（本项目修复过的问题）：三个引擎必须用同一套 SOC 上下限，否则同一个电池在不同引擎里算出不同的可用容量。现在统一从 `BESS_SOC_MIN` / `BESS_SOC_MAX` 取，默认 5% ~ 95%，DOD = 90%。

## milp.py — MILP 容量规划

**解决什么问题**：「装多大」这个问题，前面都是先枚举候选容量再逐个算。MILP 反过来——把容量本身作为决策变量，直接在全局求最优。

**模型要素**：

| 符号 | 含义 |
|---|---|
| `Z[j]` | 整数变量，第 j 种设备装几台 |
| `X_IN[i]` / `X_OUT[i]` | 第 i 个时刻从电网买 / 向电网卖的电量 |
| `Y_CH[i]` / `Y_DIS[i]` | 充电 / 放电电量 |
| `SOC[i]` | 第 i 时刻的电池电量 |
| `D[m]` | 第 m 月的最大需量（决定需量电费） |

**目标函数**：最大化 NPV

```
NPV = -(壳体成本 + 电芯成本)
      + Σ_year (售电收入 - 购电成本 - 需量电费) / (1+r)^year
      - Σ_更换年 (Pack 或电芯更换成本)
```

**约束**：

- SOC 递推：`SOC[i] = SOC[i-1] + η_c·Y_CH[i] - Y_DIS[i]/η_d`
- SOC 上下限
- 功率上限 = 台数 × 倍率 × 单台容量
- 同一时刻不能既充又放（用二进制变量或大 M 法）
- **买电量 ≤ 实际用电量**（不能买谷电转卖套利——这个约束缺失曾导致模型算出虚高收益）

**更换周期建模的坑**：Pack 每 300 个月（25 年）换一次，电芯每 96 个月（8 年）换一次。如果项目期是 25 年，`range(25)` 里根本不含 25，判定恒假 → 最贵的一次更换被静默忽略 → NPV 虚高。修法是按 `pack_months // 12` 算出更换年份，再判断是否落在项目期内。

**依赖**：`ortools`（CBC 求解器）。没装时 `solve_milp_capacity` 返回 `MilpResult(status='error')`，调用方应降级到快速排序法。

## finance.py — 财务指标

**解决什么问题**：投资 100 万，年收益 25 万，几年回本？值不值得投？

**四个指标的适用场景**：

| 指标 | 回答什么问题 | 注意 |
|---|---|---|
| `npv(rate, cashflows)` | 按折现率算，这个项目值多少钱 | 折现率取值敏感，6% 和 8% 结论可能相反 |
| `irr(cashflows)` | 年化收益率是多少 | 现金流有多个变号时可能有多个解，需要二分法兜底 |
| `calc_simple_payback(...)` | 静态几年回本 | 不考虑时间价值，适合快速判断 |
| `calc_payback_timeline(...)` | 动态几年回本 | 逐年折现累加，到转正为止 |

**IRR 的坑**：Newton 迭代在某些现金流下不收敛（尤其是首年大额支出 + 后续微利）。本项目用二分法兜底：`brentq` 在 [-0.99, 10] 区间找根，找不到返回 `None` 而不是抛异常。

**LCOE**：度电成本 = 全生命周期总成本 / 全生命周期总放电量。注意分母要用**放电量**不是充电量，中间有往返效率损耗。

## loadgen.py — 三层叠加负荷生成

**解决什么问题**：没有真实客户数据时，需要一条「像真的」负荷曲线来测算法。

**三层结构**：

```
Layer 1  省份 24h 基线 × 班制模板
         ↓  (午休衰减、非工作时段衰减)
Layer 2  设备 Markov 状态叠加
         ↓  (run / idle / off 三态 + 故障率 + 同时率)
Layer 3  日间随机噪声 + Gaussian 平滑
         ↓  (无 scipy 时回退滑动均值)
归一化到目标日均用电量
```

**为什么用 Markov 而不是简单随机**：真实工业负荷不是独立同分布的随机数，设备有「运行—待机—停机」的状态惯性和故障恢复过程。Markov 链能生成那种「连续运行几小时后突然停一段」的质感。

**参数怎么调**：

```python
_generate_load_profile(
    industry='电子制造',     # 从 INDUSTRY_PARAMS 里选，决定 base_load / shift / cv
    daily_kwh=12000,        # 日均用电量，最终会被归一化到这个值
    peak_kw=900,            # 峰值功率，用于设备功率量级校准
    n_days=30, n_points=96, # 30 天 × 15 分钟
    province='浙江',         # 用该省 24h 基线，None 表示纯班制
    weekend_atten=0.40,     # 周末衰减到 40%
    cv=0.12,                # 日间变异系数
    equipment=[{'power': 50, 'count': 4, 'simul': 0.8, 'run_prob': 0.85}],
    seed=42,                # 可复现
)
```

**注意**：`daily_kwh` 是硬约束。引擎最后会把整条曲线缩放到这个日均值，所以设备清单只影响**形状**不影响**总量**。

## diagnostics.py — 负荷指纹与行业匹配

**解决什么问题**：拿到一条陌生曲线，先判断它像什么行业——这决定了后续用哪套参数。

**指纹特征**：峰谷比、负荷率、日间变异系数、工作日/周末差异、夜间基荷占比。

**输出**：

```python
{
    'primary_tag': '🏭 连续生产',
    'secondary_tags': ['⚡ 高负荷率'],
    'confidence': 70.2,
    'features': {...}      # 原始特征值，便于调试
}
```

`match_fingerprint_to_industry()` 把指纹映射到 25 个行业里最接近的一个，返回 `(行业名, 置信度)`。

**用途**：在用户还没填行业参数时给一个合理默认值，而不是硬编码「电子制造」。

`_estimate_degradation()` 是另一个小工具：按循环次数、化学体系（LFP / NMC）、环境温度估算年容量衰减，用于 15 年项目期的收益递减建模。

## 关于这些代码的诚实说明

- 这些模块是**从生产代码剥离**的，保留了原始的函数名和参数名，包括一些历史遗留的命名不一致（`calc_npv` vs `FinanceEngine.npv`）。
- 剥离过程是自动的（AST 提取 + 依赖闭包），所以你可能看到一些只在特定分支用到的 import，或者注释里提到「v3.2fix」这类版本标记——那些是真实的修复记录，保留下来便于追溯。
- **没有单元测试**。验证方式是主程序里的 85 项巡检断言（见 `../docs/缺陷修复报告.md`）。
- 如果你发现某个算法实现和你理解的不一样，**很可能是我错了**。提个 Issue，我们一起对。
