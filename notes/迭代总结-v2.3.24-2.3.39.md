## 二、反复出现的四类模式

### 模式 A：修了报出来的那个分支，没查另一个

- 缓存键只补了报出来的两个字段（v2.3.27）
- 配对 bug 只修 `_fill_daily_table`（v2.3.25，后来发现三处）
- 24:00 只修了无年份写法（v2.3.29，有年份斜杠的一直没管）

**对策**：修任何一处，先问「还有没有同类写法」，用 grep/AST 全库扫一遍。

### 模式 B：两份实现分叉

- `PeriodType` 的 `.value`：Ultra 用了，Fusion 没用（v2.3.26）
- `timeline.py` 与主程序（v2.3.34）
- `_scan_wide_chunk` 与 `_scan_long_chunk` 一个填 dates 一个不填（v2.3.36）

**对策**：搬入型模块必须有「与源实现逐元素对比」的测试。
`verify_loadsim_equiv.py` 就是正面例子（`maxdiff=0.000e+00`）。

### 模式 C：截断出一个好看的数字，而不是报错

- `clip(upper=3.0)`（v2.3.28）—— 4 小时当 3 小时，功率高估 42%
- 移动平均 `mode='same'`（v2.3.26）—— 边界补零，曲线低头 40%
- NaN 被 `nansum` 当 0（v2.3.23 / v2.3.34）

**对策**：数据不可信时置 NaN/报错，不要「夹到合理范围」。
用户看到 142 会当成真实负荷；看到「不可信」才会去查源数据。

### 模式 D：用显示文本做逻辑判断

- `province_combo.currentText() != "无"`（v2.3.30）
- `currentText()` 判断评估策略（v2.3.16 已改 `currentData()`）

**对策**：一律用 `currentData()` / `currentIndex()`。

## 三、还剩什么

### 需要你拍板

**放电空间口径**（v2.3.32 提出，挂了 5 个版本没动）：

```
峰段负荷 500 kW，容量线 300 kW

代码现用  min(500, 300) = 300   → 1187.5 kWh
另一种    max(500−300, 0) = 200 →  775.0 kWh     差 53%
```

实测证明它不只是口径偏好：

```
容量线固定 300，只改峰段负荷
峰段 100 → 报 412.5    （负荷只有容量线 1/3，应为 0）
峰段 300 → 报 1187.5   （恰好等于容量线，仍报 1187.5）
峰段 800 → 报 1187.5   （削峰需求涨 10 倍，输出不变）
```

`min(load, cap)` 在 `load > cap` 时恒等于 `cap`，**与负荷完全无关**。

八个版本（Fusion v2.1~v2.3、Ultra v3.2.0~v3.2.8）全是这个写法。
v2.1 原注释写的是「受储能容量限制」，实际用的是容量线。

**改它会动所有已有项目的容量建议（部分差一半），所以等你点头。**

### 已知但没改

- **「周末浅灰背景」**：现在是「只要有一天是周末就整图铺 8% 灰」，
  不是给周末那几天上色。可能是作者有意的「本图含周末」提示。
- **`right=valid[-1]` 在行末真缺失时填末值**，与「整行全 NaN 保留」不一致。
- **结构债**：桌面版与 `services/` 多处同概念双实现。本轮修的三处
  分叉都源于此。

### 无法自动验证的

- 拖拽的真实手感（四种落点）
- 深色主题的实际观感
- 22 处问号弹窗的排版
- 放电口径在真实项目上的合理性

# 第三部分：v2.3.37 → v2.3.39

## v2.3.37 节假日超出年份范围时静默降级

`chinese_calendar` 1.11.0 只覆盖 2004–2026，越界抛 `NotImplementedError`：

```
NotImplementedError: no available data for year 2027,
only year between [2004, 2026] supported
```

而 `_get_day_type` 用 `except Exception` 把它吞成 `log.debug`，落到
`dt.weekday() >= 5`：

```
2027-10-01（国庆，周五）→ weekday    应该是 holiday
2028-10-01（国庆，周日）→ weekend    应该是 holiday
```

**这个 bug 要到 2027 年才发作。** 到那时用户只会觉得「节假日颜色不对」，
从「节假日判断」一路查到依赖库的年份范围，中间没有可用的线索。

2027 年的安排国务院还没发布，不是库的问题。改成「降级 + 明确告知」，
同一年只警告一次；覆盖范围不写死（全范围试一遍探出来，升级库后自动跟上）。

## v2.3.38 api 层补启动入口

`api/` 11 个文件、28 个路由、2609 行、依赖全装好，但：

```
桌面版 import api    → 零处
启动脚本            → 没有
Dockerfile          → 没有
api/app.py __main__ → 没有
```

**代码是完整的，只差一个开关。** 补了 `tools/serve_api.py`，真起服务验过：
`/api/health` 200、`/docs` 200、`/api/simulate/templates` 200 返回 25 个模板。

顺带确认 `/api/export/adopt` 的 404 是**有意的** —— 被 `LGM_DEV_TOOLS=1`
门控，没设时路由根本不存在（不是 403）。一个能扫描任意目录的端点，
不该在生产包里留下「存在但拒绝」的痕迹。

## v2.3.39 静态检查清理

ruff F401/F811/F841 从 25 条清到 0。

最值钱的一条不是死代码，是**死变量配了误导性注释**：

```python
base_power = valley_power  # 基荷=谷值
```

赋值后从不使用，但注释会让人以为「基荷 = 谷值」参与了计算——实际基荷是
后面归一化 profile 经 `valley_power + (peak − valley) × day_profile`
重新映射回来的。

没动 B904/B905/B007/B008：改它们会动 traceback、向下不兼容或纯误报，
收益小风险不对等。

# 第五部分：这一轮迭代真正学到的东西

## 五类问题模式（按出现次数）

**A. 修了报出来的那个分支，没查另一个**（4 次）
缓存键只补两个字段 / 配对只修一处 / 24:00 只修无年份 / 转置日期列只看 5 个样本

**B. 两份实现分叉**（4 次）
`PeriodType.value` / timeline / `dates` 一填一不填 / `_scan_long_chunk` vs `_scan_wide_chunk`

**C. 截断出一个好看的数字而不是报错**（4 次）
`clip(upper=3.0)` / 移动平均补零 / NaN 被 nansum 当 0 / `min(load,cap)` 与负荷无关

**D. 用显示文本做逻辑判断**（2 次）
`currentText() != "无"` / `currentText() != "满载利用率"`

**E. 静默降级不告警**（4 次）
节假日越界 / 累计示数差分失败 / 时刻无法识别丢点 / 长表不填 dates

## 一条我自己的毛病

**从代码形态推断语义，没先看调用方。** 犯过至少三次：

- v2.3.32 容量反推方向（改了业务口径还写错测试给它背书，代价最大）
- v2.3.39 `_bsim` 的 `str(c)`（以为是 NameError，实际 `cand` 是列名列表）
- 更早的月份哨兵、平段分支（推断为可达，实际是死代码）

**这条写进了 ITERATION-CHECKLIST，作为动手前的强制自问。**

## 测试的作用被反复验证

`verify_loadsim_equiv.py`（逐元素对比源实现）让 `loadsim` 没分叉；
`verify_packaged_exe.py` 的「进度窗标题」判据抓到了卡在错误对话框的进程；
`verify_discharge_caliber.py` 记录现状，改口径时会红。

**声明不算数，对比测试才算数。**
