## 一、现状诊断：**底层其实已经分好了，缺的是 UI 那一层**

很多人以为「代码烂要重写」，先看数据：

```
core/       2,690 行    业务内核：空间、时段、摄取、模型、时间网格
services/   3,265 行    服务层：配置、导出、容量、模拟、光伏反馈、任务、时间线
plotting/     807 行    绘图：曲线、字体、命名
api/        2,609 行    28 个路由，摄取/计算/绘图/导出/模拟/预览全覆盖，能真跑
ui/            89 行    空壳
tests/     20,942 行    120 个脚本
tools/      7,805 行    46 个工具
apps/       9,533 行    ← 问题全在这里
```

**业务层（6,762 行）是干净的。** 三个分层各司其职，没有循环依赖，120 个测试兜着。
**API 层（2,609 行）是完整的。** 28 个路由已经覆盖了桌面版全部业务能力。

**问题全在 `apps/` 那一个文件里：**

```
24 个类 / 343 个方法 / 9,533 行
其中 4,916 行含 Qt 调用 —— 占 58.7%
纯逻辑只有 3,455 行
```

**三个上帝类：**

| 类 | 方法数 | 行数 |
|---|---:|---:|
| `PreviewDialog` | 65 | 1,601 |
| `MainWindow` | 47 | 1,223 |
| `ProfessionalWindow` | 35 | 1,575 |

**三个巨型构造函数：**

```
PreviewDialog._init_ui          421 行
ProfessionalWindow._init_ui     349 行
MappingDialog._init_ui          200 行
```

421 行手写 `addWidget` —— 这不是「代码写得差」，这是**手写 UI 布局的必然结果**。Qt Widgets 用代码摆界面，界面一复杂就必然长成这样。

### 所以结论要修正

> **「重写底层架构」这个说法不准确。底层已经分好了。**
> **真正要重写的是：UI 表达层 + `apps/` 这个单体。**

这是好消息——**风险比预想的小得多**。业务正确性不用重新建立，那是刚花 40 个版本验证过的东西。

## 三、技术选型：Web 已排除

> **用户反馈：「之前尝试过加入 web，但是 web 不好看」**

这条否掉了原方案里的 C（纯 Web）与 D（Qt 外壳 + QWebEngine）。

**为什么 Web 套壳会难看，这是结构性的：**

```
内容区  网页渲染 —— 字体是 Chromium 的，背景可以毛玻璃，动效流畅
外壳    Qt 原生 —— 菜单栏、标题栏、滚动条、文件选择器、QMessageBox
```

**两套视觉并排出现，怎么调都不像一体。** 而且弹出对话框（保存/确认/错误）
只能是系统原生风格，与内容区必然割裂。

**剩下两个可选：**

| | A · Qt Widgets 极致化 | **B · QML + Qt Quick** |
|---|---|---|
| 周期 | 3–4 周 | 5–7 周 |
| 体积 | 不变（142 MB） | +30 MB |
| 业务风险 | 零 | 零 |
| UI 天花板 | **中** | **高** |
| 视觉一致性 | 单套（QSS） | 单套（QML 渲染） |

### 为什么 A 达不到你要的水准

QSS 是 CSS 的子集，**做不了这些**：

- 真毛玻璃（任意元素后景模糊）
- GPU 合成的流畅形变动画
- 粒子系统
- 着色器（自定义光照/噪波/渐变流动）
- 主题切换时的自动过渡
- 421 行的 `_init_ui` 拆完还是「用代码摆控件」

### QML 能做的

```
MultiEffect.blur              任意元素真模糊（毛玻璃）
ParticleSystem                内置粒子（发光点、能量流动）
ShaderEffect                  GLSL 着色器（渐变流动、噪波、光晕）
states + transitions          状态驱动动画（切主题/切模式自动过渡）
GPU 合成                       60fps 不卡
声明式布局                     类似 CSS，不再是 addWidget 地狱
```

**关键优势：它和 Qt 是同一套渲染管线。** 没有「两套视觉并排」的问题——
窗口、菜单、对话框、内容区全部由同一个引擎画。

### QML 的真实难点（不掩饰）

| 难点 | 影响 |
|---|---|
| 表格 | Qt Quick 的 `TableView` 可用，但样式定制比 QTableWidget 麻烦；空间表/逐日表要用自定义 delegate |
| 布局调试 | 比 CSS 难，QML 的绑定错误不会在编译期报 |
| 中文排版 | 需要显式设字体与行高，不自动跟随系统 |
| 我的熟练度 | 写 QML 不如写 CSS 快，前期出活会慢 |
| 五档 DPI | 需要逐档验证（这台机器 175%） |

**这些都能解决，但都会花时间。** 6–8 周里大概有 1 周是缴这些学费。

## 四、推荐：B · QML + Qt Quick

### 为什么不是 A

即使 A 只需要 3–4 周、体积不变、风险最低，但它在「UI 最极致」这一项上直接出局。
你为这个重构定的第一条就是「最极致最顶级的艺术 UI」——A 做不到，那就是没达成目标。

### 为什么 B 能达成目标

**① 单套渲染管线，没有 Web 那种割裂感**

窗口、菜单、对话框、内容区——全部由 Qt Quick 场景图绘制。没有「一半原生一半网页」。

**② 视觉能力覆盖你的审美**

| 你要的 | QML 里的实现 |
|---|---|
| 毛玻璃质感 | `MultiEffect { blurEnabled: true }` |
| 黑金发光 | `ShaderEffect` + 外发光 + 发光渐变 |
| 冰蓝玻璃 | 半透明底 + 模糊 + 细边框 + 内高光 |
| 未来科技感 | `ParticleSystem` 粒子、流光、扫描线 |
| 有重量感的动效 | `Behavior` / `SpringAnimation`（真物理弹簧） |
| 深浅双主题 | 自定义 `Theme` 单例，`states` 切换自动过渡 |
| 高信息密度 | 自定义 delegate，不受系统控件高度限制 |

**③ 性能**

Qt Quick 走 GPU 场景图，动画不掉帧；曲线用 `Canvas` 或预渲染 `QQuickPaintedItem`。

**④ 稳定性**

无 HTTP、无端口、无外部进程、无 Chromium 内核。PyInstaller 单链路打包。

**⑤ 维护性**

QML 是声明式：界面长什么样、状态怎么变，直接写出来。不再有 421 行的 `_init_ui`。
改一个控件不用在 400 行里找位置。

### 业务零风险

`core/` + `services/` + `plotting/` **一行不动**。那 6,762 行是 40 个版本、120 个测试验证过的正确性——重写它们等于把刚建立的可信度丢掉。

QML 与 Python 的接法：**`QQmlApplicationEngine` + 注册 Facade 对象**，进程内直接调，不走网络。
```
QML (表现)
   ↓ 属性绑定 / 信号槽
ApplicationFacade (薄适配层，新增)
   ↓ 直接函数调用
core / services / plotting（不动）
```

## 五、迁移路径（怎么保证不倒退）

**核心原则：业务内核冻结，UI 层新建，两者通过一层薄适配器对接。**

```
阶段 0   冻结基线（1 天）
         ├─ 打 tag v2.3.40-final
         ├─ 120 个测试全绿存档
         └─ 记录当前所有输出的基准值（曲线图、空间表、报告）
                    ↓
阶段 1   抽出适配层（3–5 天）
         ├─ 定义 ApplicationFacade：UI 只调这一层
         ├─ 现有 Qt 窗口改为调 Facade（行为不变，测试仍绿）
         └─ 目的：证明 Facade 覆盖了 UI 需要的全部能力
                    ↓
阶段 2   新前端骨架（1–2 周）
         ├─ 设计系统：色彩/字号/间距/组件/动效规范
         ├─ 深浅双主题、毛玻璃、发光 token 化
         └─ 三个主界面：主窗口 / 预览 / 专业分析
                    ↓
阶段 3   功能迁移（3–4 周）
         ├─ 按模块迁移：读文件 → 映射 → 预览 → 专业分析 → 导出
         ├─ 每迁一个模块，与旧版做**逐像素/逐数值**对照
         └─ 双轨并行：新旧可切换，随时回退
                    ↓
阶段 4   收尾（1 周）
         ├─ 删旧 UI 代码
         ├─ 打包链路重建、体积/启动/内存实测
         └─ 基准值全量回归
```

**关键判据：每个阶段结束，120 个测试必须全绿。测试红了就是倒退，当场回头。**

## 附：为什么我不建议「全部重写」

历史上有个著名案例：Netscape 1998 年决定把 4.0 全部重写，结果三年没出货，市占率从 90% 掉到接近零。

**重写的诱惑在于「从零开始一定更干净」，代价在于「你已经验证过的东西全部作废」。**

这个项目刚花 40 个版本修了 40 个静默失败，120 个测试逐个证明它们不再发生。**这些测试是资产，不是负担。** 保留 `core/`，它们全部继续有效；重写 `core/`，它们全部要重写——而且重写后的测试还有一批会写错（v2.3.32 那次我给错误口径背书就是例子）。

**UI 层不同**：它没有「业务正确性」这回事，只有「好不好看、顺不顺手」。重写它是纯收益。
