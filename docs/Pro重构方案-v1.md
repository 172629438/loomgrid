# Fusion → Pro 重构方案 v1

> 2026-11-10 · 目标：性能最强 / 稳定性最强 / 维护性最好 / 最极致 UI
> 本文先给诊断与方向，待拍板后再出详细设计。

---

## 一、现状诊断：**底层其实已经分好了，缺的是 UI 那一层**

很多人以为「代码烂要重写」，先看数据：

```
core/       2,690 行    业务内核：空间、时段、摄取、模型、时间网格
services/   3,265 行    服务层：配置、导出、容量、模拟、光伏反馈、任务、时间线
plotting/     807 行    绘图：曲线、字体、命名
api/        2,609 行    28 个路由，摄取/计算/绘图/导出/模拟/预览全覆盖，能真跑
ui/            89 行    空壳
tests/     20,942 行    120 个脚本
tools/      7,805 行    46 个工具
apps/       9,533 行    ← 问题全在这里
```

**业务层（6,762 行）是干净的。** 三个分层各司其职，没有循环依赖，120 个测试兜着。
**API 层（2,609 行）是完整的。** 28 个路由已经覆盖了桌面版全部业务能力。

**问题全在 `apps/` 那一个文件里：**

```
24 个类 / 343 个方法 / 9,533 行
其中 4,916 行含 Qt 调用 —— 占 58.7%
纯逻辑只有 3,455 行
```

**三个上帝类：**

| 类 | 方法数 | 行数 |
|---|---:|---:|
| `PreviewDialog` | 65 | 1,601 |
| `MainWindow` | 47 | 1,223 |
| `ProfessionalWindow` | 35 | 1,575 |

**三个巨型构造函数：**

```
PreviewDialog._init_ui          421 行
ProfessionalWindow._init_ui     349 行
MappingDialog._init_ui          200 行
```

421 行手写 `addWidget` —— 这不是「代码写得差」，这是**手写 UI 布局的必然结果**。Qt Widgets 用代码摆界面，界面一复杂就必然长成这样。

### 所以结论要修正

> **「重写底层架构」这个说法不准确。底层已经分好了。**
> **真正要重写的是：UI 表达层 + `apps/` 这个单体。**

这是好消息——**风险比预想的小得多**。业务正确性不用重新建立，那是刚花 40 个版本验证过的东西。

## 三、四个方向，逐个说代价

### A · Qt Widgets 极致化（保守）

**做法**：留在 PySide6，把 `apps/` 拆成模块，建立设计系统，QSS 深度定制，QGraphicsView 做动效。

| | |
|---|---|
| 周期 | 3–4 周 |
| 体积 | 不变（142 MB） |
| 业务风险 | 零 |
| UI 天花板 | **中** |

**天花板在哪**：QSS 是 CSS 的子集——**没有真毛玻璃（backdrop-filter）、没有流畅的形变动画、没有粒子系统、没有 GPU 合成**。你的审美偏好（黑金发光、冰蓝玻璃、未来科技感）在这个框架里只能做七八成。

**421 行的 `_init_ui` 会变成什么**：拆成 20 个小方法，但它还是「用代码摆界面」。可读性提升，表现力不变。

---

### B · QML + Qt Quick（中间）

**做法**：UI 层换 QML（声明式，类似 CSS 的写法思路），Python 后端通过 `QQmlApplicationEngine` 暴露。

| | |
|---|---|
| 周期 | 5–7 周 |
| 体积 | +30 MB |
| 业务风险 | 零 |
| UI 天花板 | **高** |

**能做**：GPU 渲染、原生动画曲线、`MultiEffect` 模糊（真毛玻璃）、粒子、流畅转场。

**代价**：QML 的布局调试比 CSS 难；组件生态比 Web 小；我写 QML 的熟练度不如 CSS，出活会慢。

---

### C · 纯 Web + 本地后端（激进）

**做法**：前端全新（HTML/CSS/Canvas/WebGL），后端直接用现有 `api/` 28 个路由，用 Electron 或 pywebview 打包。

| | |
|---|---|
| 周期 | 5–7 周 |
| 体积 | Electron +150 MB / pywebview 用系统 WebView2 ≈ +0 |
| 业务风险 | **零**（api/ 已有） |
| UI 天花板 | **最高** |

**能做**：`backdrop-filter` 真毛玻璃、CSS 动画、WebGL 粒子、Canvas 高性能曲线（10 万点流畅）、深浅主题用 CSS 变量一键切换。

**代价**：
- Electron 体积大；pywebview 依赖系统 WebView2（Win10 1803+ 自带，老机器可能要装）
- 需要本地 HTTP 服务 → **端口占用、杀毒软件拦截、防火墙弹窗**，这是实打实的稳定性风险
- 失去原生窗口行为（拖放、系统菜单、任务栏跳转列表）需要额外适配

---

### D · Qt 外壳 + QWebEngineView 内容区（混合）

**做法**：主窗口还是 Qt（原生菜单/托盘/拖放/系统集成），**内容区**用 QWebEngineView 加载本地前端，Python ↔ JS 走 `QWebChannel` 直接桥接（**不需要 HTTP 端口**）。

| | |
|---|---|
| 周期 | 6–8 周 |
| 体积 | **+100 MB**（QtWebEngine） |
| 业务风险 | 零 |
| UI 天花板 | **最高** |
| 稳定性 | **高**（无端口、无外部进程、单进程模型） |

**为什么它比 C 稳**：没有 HTTP 服务、没有端口冲突、没有防火墙弹窗。QWebChannel 是进程内桥接。

**代价**：体积从 142 → 约 240 MB；QtWebEngine 在 PyInstaller 下有打包坑（ICU 数据、locales、资源路径）；冷启动慢 1–2 秒；内存占用上升（Chromium 内核）。

## 四、我的推荐

**推荐 D，理由排序如下：**

**① 你的要求在 D 上冲突最小**

| 你的要求 | A | B | C | D |
|---|:--:|:--:|:--:|:--:|
| 性能最强 | ○ | ● | ● | ● |
| 稳定性最强 | ● | ● | ✕ | ● |
| 维护性最好 | ○ | ○ | ● | ● |
| 最方便我迭代 | ✕ | ○ | ● | ● |
| UI 最极致 | ✕ | ● | ● | ● |

A 在「UI 最极致」上直接出局；C 在「稳定性」上失分（端口/外部进程）；B 在「最方便我迭代」上不如 Web。

**② 业务零风险**

`core/` + `services/` + `plotting/` **一行不动**。那 6,762 行是 40 个版本、120 个测试验证过的正确性——重写它们等于把刚建立的可信度丢掉。

**③ 现有资产直接用**

`api/` 28 个路由已经覆盖摄取/计算/绘图/导出/模拟/预览。Web 前端可以直接消费它——或者更稳的做法：**QWebChannel 直接调 Python 层，连 api/ 都不用走 HTTP**。

**④ 我能把 UI 做到你要的水准**

毛玻璃、发光、粒子、深色主题、高信息密度——这些在 CSS/Canvas 里是我的主场。QSS 做不了，QML 能做但慢。

## 五、迁移路径（怎么保证不倒退）

**核心原则：业务内核冻结，UI 层新建，两者通过一层薄适配器对接。**

```
阶段 0   冻结基线（1 天）
         ├─ 打 tag v2.3.40-final
         ├─ 120 个测试全绿存档
         └─ 记录当前所有输出的基准值（曲线图、空间表、报告）
                    ↓
阶段 1   抽出适配层（3–5 天）
         ├─ 定义 ApplicationFacade：UI 只调这一层
         ├─ 现有 Qt 窗口改为调 Facade（行为不变，测试仍绿）
         └─ 目的：证明 Facade 覆盖了 UI 需要的全部能力
                    ↓
阶段 2   新前端骨架（1–2 周）
         ├─ 设计系统：色彩/字号/间距/组件/动效规范
         ├─ 深浅双主题、毛玻璃、发光 token 化
         └─ 三个主界面：主窗口 / 预览 / 专业分析
                    ↓
阶段 3   功能迁移（3–4 周）
         ├─ 按模块迁移：读文件 → 映射 → 预览 → 专业分析 → 导出
         ├─ 每迁一个模块，与旧版做**逐像素/逐数值**对照
         └─ 双轨并行：新旧可切换，随时回退
                    ↓
阶段 4   收尾（1 周）
         ├─ 删旧 UI 代码
         ├─ 打包链路重建、体积/启动/内存实测
         └─ 基准值全量回归
```

**关键判据：每个阶段结束，120 个测试必须全绿。测试红了就是倒退，当场回头。**

## 六、我能承诺的与不能承诺的

**能承诺：**
- 业务计算**输出不变**（有基准值和测试兜着）
- 每个模块迁移后可与旧版逐项对照
- 任何阶段可回退（旧 UI 保留到阶段 4）

**不能承诺：**
- **一次做完全部**——这是 6–8 周的工程量，不是一次对话
- **UI 一定合你眼缘**——审美是主观的，我只能保证「按设计规范做、每次交付可评点、改起来快」
- **零 bug**——重写就是引入新问题的过程，只能靠测试和逐步对照压住

## 附：为什么我不建议「全部重写」

历史上有个著名案例：Netscape 1998 年决定把 4.0 全部重写，结果三年没出货，市占率从 90% 掉到接近零。

**重写的诱惑在于「从零开始一定更干净」，代价在于「你已经验证过的东西全部作废」。**

这个项目刚花 40 个版本修了 40 个静默失败，120 个测试逐个证明它们不再发生。**这些测试是资产，不是负担。** 保留 `core/`，它们全部继续有效；重写 `core/`，它们全部要重写——而且重写后的测试还有一批会写错（v2.3.32 那次我给错误口径背书就是例子）。

**UI 层不同**：它没有「业务正确性」这回事，只有「好不好看、顺不顺手」。重写它是纯收益。
