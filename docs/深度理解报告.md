### 3.2 两套并行的分析架构

Ultra 里同一个"充放电空间"有两份实现，这是理解全部代码的关键分叉：

| | 快速版 | 精算版 |
|---|---|---|
| 函数 | `compute_daily_spaces` L9311 | `compute_segmented_spaces` L9405 |
| 粒度 | 整日汇总，按充电/放电时段做掩码 | 逐段计算，每段独立出空间与标签 |
| 用途 | 报告/诊断/外部引擎（`compute_segmented_spaces` 也被 `EnergyStorageEngineer.diagnose` 调用 L30372） | ProfessionalWindow 交互界面（L14139、L15109） |
| 跨午夜 | 不做拆分（靠 mask 覆盖） | 拆成 [start,24) + [0,end) 两个子区间 |

**两版差异（重要）**：跨午夜段在精算版里会产生**两个独立的段数组**（Ultra 版 append 在子区间循环内），而融合版用 `space +=` 累加成一个。后果是 Ultra 精算版会遇到"同一标签出现两次"（两个"充电1"），而 `_compute_segment_power_summary`（L14246）正是用 label 做字典键取最小值 —— 重复 label 会互相覆盖。**这条列为待核缺陷 P-01。**

## 四、核心算法精读

### 4.1 充放电空间的物理定义（所有分析的地基）

时间步长 `dt`：首尾用相邻差，中点用 `dt[i]=(h[i+1]-h[i-1])/2`（L9316-9321 / L9257 的 `_compute_time_dt`）。

**Mode A（需量管理 / 峰谷套利）**
- 充电空间 = `Σ max(容量线 − 负荷, 0) × 充电时段掩码 × dt`  ← **不乘充电效率**
- 放电空间 = `Σ min(max(负荷,0), 容量线) × 放电时段掩码 × dt × 放电效率`
- 业务含义：充电空间 = 电网侧还能往里灌多少电；放电空间 = 电池侧能放出多少、供到负荷侧

**Mode B（纯光伏）**
- 充电 = `Σ min(额定功率, 负负荷) × dt × 充电效率`（负负荷＝光伏返送）
- 放电 = `Σ min(额定功率, 正负荷) × dt × 放电效率`

**Mode C（光伏+峰谷）**
- 充电 = `min(额定, 负负荷) × max(充电时段掩码, 负荷<0)`，再与容量线约束取 min
- 放电 = `min(额定, 正负荷) × 放电时段掩码`，同样受容量线约束

**效率常量体系（有两处定义，后定义覆盖前定义）**
- L219-230：`BESS_EFF_CHARGE=0.93`、`BESS_EFF_DISCHARGE=0.93`、`BESS_DOD_DEFAULT=0.95`
- L1487-1489：再次定义 0.93/0.93，`BESS_EFF_ROUNDTRIP=0.865`，注释「v2.23 从 0.95 下调至业界实测值」
- 实际生效的是 L1487 之后的 0.93/0.93（Python 后赋值覆盖）。**两处重复定义是隐患 P-02。**

**SOC 递推口径（自洽）**：`_recalc_spaces`（L14172）里 `delta = c_segs × η_charge`、`delta = −d_segs / η_discharge`。这正好把"电网侧口径"换算成"电池侧 SOC 变化"，与上面的充电不乘 η／放电乘 η 一致。**这一段是自洽的。**

### 4.2 容量反推

`calc_capacity_for_days(target_days, charge, discharge)`（L9385）：
取 `min(充, 放)` 的逐日序列升序排序，返回第 `n − target_days` 位。
语义是**分位数**：要保证全年 `target_days` 天能满充满放，容量就取这个分位点 —— 相当于允许 `n − target_days` 天"吃不饱"。这是"满充满放天数法"的标准实现。

`calc_days_for_capacity(cap, ...)`（L9398）：同时满足 `充 ≥ cap` 且 `放 ≥ cap` 的天数。

### 4.3 瓶颈月法（这是本工具的业务灵魂）

`_compute_segment_power_summary`（L14246，177 行）：
1. 按月的充放电段总量 ÷ 天数 ÷ 段时长 = 该段平均功率
2. 按电价政策分组：春秋(3-6,10-11) / 夏季(7-9) / 冬季(12,1) / 二月（`TARIFF_GROUPS`，L14252）
3. **组内取最小值**作为该段的可行功率 → 最小值的那个月就是"瓶颈月"
4. ratio ≥0.90 判"充裕"，≥0.75 判"偏紧"，<0.75 判"严重不足"
5. 顺带产出额定功率建议 = 组内放电段最小值中的最大值

设计意图很明确：储能容量要按**全年最不利的那个月**定，否则某几个月会吃不饱。这套逻辑是财务可信度的来源，也是给客户讲"为什么不是按平均值配"的答案。

### 4.4 经济模型（calc_economic_summary, L17133, 211 行）

收益三源，互斥校验：
- **套利**：A 模式 `放电量×峰价 − 充电量×谷价`；B 模式 `放电量×峰价`（光伏充电零成本）；C 模式 `放电×峰价 − 充电×平价`
- **需量节省**：逐月 `min(可削减需量, 额定功率, 当月峰值) × 需量电价`，全年累加（v2.20 起逐月算，替代 `×12` 的粗算）
- **容量电价**：仅 `storage_type='grid_side'` 可领（114 号文第三条），用户侧强制为 0，避免与套利叠加

成本与税：
- 增值税等效 **6.5%**（13% 即征即退 50%）
- 年运维 **2.5% CAPEX**，所得税 **25%**，直线折旧，残值 **5%**
- 电池：`日循环 = min(总充,总放)/(容量×DOD)`，再用 rainflow 修正取较大值；寿命 = `min(循环寿命/年循环, 15 年日历上限)`；到期更换按 **40%** CAPEX

指标：NPV（逐年贴现）、IRR（牛顿法 ≤50 次，未收敛/负值打 `irr_risk` 标）、回收期（累积现金流线性插值）、LCOS（L30778）。

**关键性质（必须知道）**：这套是「**年化静态 + 月级需量**」口径 —— 用全年总充放量乘电价，不是逐时仿真。逐时的是另外三条线：`simulate_daily_dispatch`（逐日 SOC 仿真）、`optimal_dispatch_lp`（LP 全局最优）、`solve_milp_capacity`（MILP 8760h）。**同一个界面上的数，背后可能是三种不同精度，对外报数时要说清用的是哪一条。**

⚠️ **待核缺陷 P-03（效率重复折算）**：`total_charge_kwh` 来自 `compute_segmented_spaces`，已是"电网侧"口径（未乘 η）；但经济模型又做 `grid_charge = total_charge / η`、`grid_discharge = total_discharge × η`。若上述口径判断成立，则充电成本被高估 1/0.93 ≈ 7.5%、放电收益被低估 7%，套利收益合计偏低约 14%。需要用一组固定负荷实测核对（构造已知充放量的数据，比对程序输出与手算）。

### 4.5 需量计算

- `_calc_sliding_window_demand`（L8799）：滑窗平均功率取最大，行业标准口径
- `calc_fixed_window` / `calc_sliding_window` / `compare_windows`（L32350 起）：固定窗口 vs 滑动窗口对比
- `_analyze_demand_characteristics`（L4771）：年最大需量 + 削减潜力
- 图表上的需量线用的是**滑动窗口**（L9001 附近调用），与电网结算口径一致

### 4.6 光伏出力（calc_pv_hourly_output, L3020, 167 行）

四种算法可选，含晴空辐照 `_haurwitz_clear_sky_ghi`（L2981）与 PVGIS API 实测路径 `_simulate_pv_pvgis`（L29582）。光伏已应用时，`_get_work_data`（L13897）返回净负荷 `load − pv`，逐月独立 profile，分辨率不匹配时线性插值（注释说明：线性插值精度 >98%，优于前向填充）。

### 4.7 数据质量三件套

1. `_screen_load_data_quality`（L4531）：逐时刻 IQR，超 `Q3+3IQR` 用中位数替换；IQR=0 退 MAD×10；MAD 也 0 时用"偏离中位数 >300% 且 >1kW"绝对阈值
2. `_clean_asset_data_mad`（L4577）：整日维度 —— 对中位日算欧氏距离，MAD 阈值（默认 3.0 ≈ Z-score 4.45）判异常日，`replace` 用中位日替换 / `exclude` 剔除；少于 5 天拒绝清洗
3. `_compute_data_health_score`（L29995）：0–100 → A–F 分级，含行业基准参照

**设计判断**：清洗默认关闭，是"用户显式开启"的动作，不会偷偷改数 —— 这点对方案可信度很重要。

### 4.8 调度与容量规划：三套引擎并存（关键结构认知）

这层不是一套模型，而是三套引擎叠着长出来的，**各带一套自己的 SOC、效率、时间步口径**：

| 维度 | 贪心 | LP | MILP |
|---|---|---|---|
| 代表函数 | `simulate_daily_dispatch` L29425、`_dispatch_greedy` L31181、`greedy_dispatch_annual` L33189 | `optimal_dispatch_lp` L33320、`_joint_optimize_lp` L34717 | `_solve_milp_one_day` L31136、`solve_milp_capacity` L31839 |
| 决策方式 | 先直供→再充→再放→再购 | 全体同时决策 | 全体同时决策 + 整数选型 |
| 时间步 | `24/n_pts` 自适应 | `dt` 传参（默认 0.25） | 单日固定 0.25 / 8760 逐时 |
| SOC 区间 | 5%~95%（greedy）/ 10%~90%（daily） | 10%~90%，初值 20% | 5%~95%，初值 10% |
| 往返效率 | 0.90（√0.9 拆分，正确） | 0.95×0.95=0.9025 | 0.93²=0.865 |
| 需量建模 | 无 | 有（peak 变量） | 有（月需量 D[m]） |
| 充放互斥 | 天然互斥 | 无（仅 `ch+dis≤P`） | 天然互斥 |
| 末态约束 | 无 | 无（最优解会放空） | 强制回位 |

**结论：同一个界面上看到的"收益"，背后可能是四种效率口径之一（0.81 / 0.865 / 0.90 / 0.9025）。对外报数时必须说明用的是哪条。**

### 4.9 光伏与需量

- 光伏四算法：晴空辐照 `_haurwitz_clear_sky_ghi`（L2981）+ 正弦模板修正（倾角、温度降额 0.9125、日照时数钳 6~16h）+ PVGIS 在线（L29582，2020 单年当典型年）+ 统一入口 `calc_pv_hourly_output`
- PVGIS 失败回退离线模型时**没传 city / latitude**（L29604-29626），倾角退回 25°、峰值日照退回 4.0 —— 用户以为同一个配置，实际换了一套假设
- 需量两套：`calc_sliding_window` 跨日连续滚动；`compare_demand` 按日 `pad(mode='edge')` 居中滑窗。日界处结果必然不同，程序把差异叫"偏差%"，实为算法定义不同
- `calc_demand_charge` 用全局最大需量×单价，`analyze_from_series` 却把它写作"月基本电费"（L32485）—— 只有单月数据时成立

## 五、配置与状态治理

`Config`（L7008，798 行）是整个程序的"记忆器官"：

- **版本 20**，迁移链 v14→v20，每步独立 try，成功即持久化版本号（"渐进式迁移"，避免一步失败全回滚）
- 结构：`price_strategies{省: {type, groups[{name,months,periods}], seasons}}` + `app_settings` + `column_fingerprints` + `fingerprint_usage`
- **保存**：写 tmp → `flush()+fsync()` → 旧文件带时间戳备份 → `os.replace` 原子替换（跨盘失败回退 `shutil.move`）
- **恢复**：`_restore_backup` 逐个读备份，每个都过 Schema 校验，全失败才用硬编码默认
- **审计**：`logs/audit/operations.log`，超 10MB 截断保留尾 5MB 且跳整行边界
- 备份保留：每日 5 份 + 每周 3 份

**列映射推荐 4 层**（`recommend`, L7417）：
1. `文件名模式|sheet` 精确匹配
2. 列指纹精确匹配（`date|time|asset|load|format_type`）
3. 模糊指纹：逐字段 `SequenceMatcher` 均值 + 使用次数奖励（≤0.15），阈值 0.75，`format_type` 必须完全一致
4. 全局列名相似度 ≥0.7 兜底

这套设计的效果是：同类报表第二次拖进来基本不用再配映射。`FileMemory`（v3.2 新增，L385）更进一步 —— 用「路径+大小+修改时间」的 SHA256 前 16 位做文件指纹，记住每个文件的映射与设置。

## 六、工程实现（这部分是代码水准的体现）

**并发模型三层**
| 层 | 机制 | 位置 | 目的 |
|---|---|---|---|
| 扫描 | 主线程串行（v2.23 起） | `_scan_and_prepare` L26279 | 规避 pandas C 扩展多线程 segfault |
| 预览渲染 | 子进程池 + Figure 复用 | `_process_render_in_subprocess` L12740 | 隔离 matplotlib，避免主进程内存膨胀 |
| 出图 | `ProcessPoolExecutor(max_tasks_per_child=50)` | `_execute_plot_tasks` L26751 | 子进程定期回收，防 matplotlib 泄漏 |

**性能细节**（说明这版被认真调过）
- `_init_render_worker` L12725：把 `OMP/MKL/OPENBLAS/NUMEXPR/VECLIB` 线程全部压到 1 —— 注释写明"4 子进程 × 8 核 MKL = 32 线程超订 → CPU 颠簸 → 实际性能倒退 30-50%"
- `_bind_performance_cores`（L12354）+ `_win_boost_process_performance`（L12415）：绑 P-core、提优先级、禁功率节流
- `_detect_discrete_gpu` / `_enable_discrete_gpu_rendering`（L12518/12600）：检测独显并优先使用
- `_draw_curves_core` 用 `LineCollection` 批量构建（替代逐条 plot），最多 5 万段上限保护
- `_get_available_memory` 5 秒缓存；`_adjust_for_memory` 按可用内存自动降并行度

**容错惯例**
- 大量 `try/except` + `log.debug(..., exc_info=True)`，静默异常带栈
- `safe_ui_op` 装饰器（L546）：UI 回调 crash 边界
- `_translate_error`（L3370）：把异常翻译成人话
- 尺寸/形状守卫遍布：`load_array` 与 `dates` 长度不一致自动截断并 warn；`seg_counts` 与 `all_colors` 维度不匹配时诊断输出

同一套业务，两套代码，风格差异明显：

| 维度 | Ultra v3.2 | 融合版 v2.3 |
|---|---|---|
| 总量 | 35363 行 / 96 类 | 10421 行 / 32 类 |

| 缓存 | MemoryLimitedCache（按字节） | MemoryLimitedCache（按字节）+ PreviewRenderTask 指纹比对 |

两处代码里都明确写了「本函数 Pro(95行) 与 Ultra(200行) 独立实现, 修改任一侧需同步更新」——说明这是有意识的双轨，不是意外分叉。

## 八·五、UI 层与并发架构（通读结论）

这一层的真实复杂度不在"画界面"，而在两件事：**两条渲染通道**和**三处握手机制**。

### 两条渲染通道（关键：它们不是同一条）

| | 预览通道 | 导岀通道 |
|---|---|---|
| 调度器 | `_PreviewRenderScheduler`（L12803，427 行） | `_execute_plot_tasks`（L26751） |
| 并发 | `ProcessPoolExecutor(min(4,max(2,cpu//2)), max_tasks_per_child=50)` + 取数线程池 | `ProcessPoolExecutor(min(workers,cpu-1), max_tasks_per_child=50)` |
| 缓存 | 参数指纹 hash + `_pixmap_cache` LRU + `_rendering_set` 闸门（4） | 无缓存，直接落盘 |
| 容错 | `BrokenProcessPool` 三次重建池 + 递增 sleep | 单任务 300s 超时 |
| 输出 | QPixmap → QGraphicsView（支持 plotly 双模） | PNG/SVG/PDF 文件 |

**为什么重要**：预览里看到的图与导出得到的图，走的是两套代码路径。修一边不保证另一边同步（P-18 就是这种分叉的后果：预览有拟合曲线，导出没有）。

### 三处握手（主线程 ↔ 处理线程）

1. `dialog_event` 轮询（0.5s 步长）+ 映射超时（默认 60s，L26280-26300）
2. 预览等待 300s 超时即取消（L26468-26473）
3. 递归深度守卫：预览交互超 10 层强制停（L26447-26450）

设计判断：用"事件 + 超时"而不是 Qt 信号阻塞式回调，好处是处理线程永不死锁，代价是每个交互点都要手写超时与状态机，—— 这也是这个文件为什么会有 3.5 万行的直接原因。

### 启动链路（main, L28506）

三阶段：① 版本检查 + `mp.freeze_support()` + ANGLE/D3D11 + `QSurfaceFormat(4.1 Core)` + 独显检测 + QApplication + Splash 首帧；② `QTimer.singleShot(550, _deferred_init)` 在动画期间后台完成日志、excepthook、临时文件清理、`timeBeginPeriod(1)`、性能增强、主题、依赖检查、MainWindow 构造；③ 动画结束后 `window.show()` + BlueprintTransition + 欢迎导览。

视觉层自成体系：`DesignTokens`（L981，349 行，含深浅两套色板与 253 行 QSS 生成）、`HslAnimator`（50ms 全局色相）、`RippleButton`、`GlowProgressBar`、`ParticleOverlay`、`Toast`/`ToastManager`、`Anim`（GSAP 风格动画工厂，L3462）。这是"产品感"的来源，也是改样式时最容易被忽略的耦合点（QSS 由代码生成，不是在 .qss 文件里）。

## 九、维护与接手建议

1. **先跑通再改**：Ultra 依赖 PySide6 + pandas + numpy + scipy + chardet + chinese_calendar + psutil + openpyxl/calamine，缺哪个都会降级（不崩但功能缺）。
2. **改算法只动一处**：空间计算有"快算/精算"两份、Ultra/融合版两套。改前先确认影响面，两边的注释都写了同步要求。
3. **别按文件名判版本**：以文件头注释 + `ULTRA_VERSION` 为准。融合版目录名与内部版本号错位。
4. **配置是活的**：`column_mapping_config.json` 带 v20 迁移链，手改要留版本号，否则 `_migrate` 会重复执行。
5. **效率常量改一处不生效**：必须同时改 L219-230 与 L1487-1489（P-02）。
