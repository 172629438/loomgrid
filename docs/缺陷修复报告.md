## 二、最严重的一条：P-29（整块功能是死代码）

**现象**：Ultra v3.2 有 11 个方法、350 行，写在模块级函数 `fuse_load_curves` 的 `return` 之后，语法合法但永不执行。

**为什么会崩**：UI 层直接持有这些方法的引用——
- `L14804`：`self.pv_import_btn.clicked.connect(self._on_import_pv)`

这些是**立即求值**的属性访问。`ProfessionalWindow` 上不存在这些属性 → 构建左面板时抛 AttributeError。

**修法**：把 350 行整体搬回 `ProfessionalWindow` 类体内。

**验证**：
```

11 个方法全部归属 ProfessionalWindow ✓

```

**附带说明**：搬运过程翻过一次车——第一版脚本切片拼接错误（`lines[dead_end+1:insert_at]` 为空切片），导致代码块被复制两份且插入位置错误。已从 `.bak-before-move` 回滚，改为「先删后按原索引插入」重做，当前文件是回滚后重做的正确版本。

### 3.4 特性回归补齐（v3.2 丢失了 v3.0 的强化引擎）

**发现方式**：用 AST 对比四个版本的方法集合，发现备份程序 v2.29+ 有两个函数在 Ultra v3.2 里完全不存在：
`_generate_load_profile`、`simulate_to_csv`。

**核实结果**：这不是改名。v3.2 的 `generate_load_profile(config)` 是**简化版**（单层模板 × 月系数），而 v3.0 的 `_generate_load_profile(...)` 是**三层叠加引擎**：

1. 第一层：省份 24h 基线 × 班制模板（含午休衰减、非工作时段衰减）
2. 第二层：设备 Markov 状态叠加（run/idle/off 三态 + 故障率 + 同时率）
3. 第三层：日间随机噪声 + Gaussian 平滑（无 scipy 时回退滑动均值）

外加 `weekend_atten`（周末衰减）、`cv`（变异系数）、`province`（省份基线）、`use_season`（季节修正）、`equipment`（设备清单）、`seed`（可复现）共 6 个 v3.2 没有的能力。

**处理**：从备份程序原样回填 `INDUSTRY_PARAMS`（10 行业）+ `_generate_load_profile` + `simulate_to_csv`，共约 165 行。两个新函数与现有 `generate_load_profile` **并行存在**，不改动后者的任何调用方。

**实测证据**（`verify_feature_restore.py`）：
```

日均电量归一化到目标          ✓  日均=[10000,10000,10000,10000,10000]
时间标签 96 个               ✓  首=00:00 末=23:45
设备 Markov 叠加生效          ✓  平均差异=31.836 kW（同 seed 下加设备）
simulate_to_csv 生成文件      ✓  2465 字节 / 4 行 / 97 列
```

## 四、口径变更：SOC / DOD（P-23，经用户授权拍板）

**原状态**：同一块电池三个保护值 —— 全局 `BESS_SOC_MIN=0.00`、`_dispatch_greedy` 写死 5%、`simulate_daily_dispatch` 与 `_simulate_soc_for_rainflow` 写死 10%。对外说「DOD 95%」没有唯一依据。

**现口径**：
```
BESS_SOC_MIN = 0.05    # 留 5% 底部保护
BESS_SOC_MAX = 0.95
BESS_DOD_DEFAULT = 0.90
```
理由：LFP 放空到 0% 会加速衰减；工商业储能产品普遍留 5% 保护；DOD 90% 是设计规范常用值。

**行为影响（必须知道）**：容量推荐 = 日需求 / DOD。DOD 从 0.95 降到 0.90，**同一日需求下推荐安装容量约 +5.6%**，投资收益指标随之变化。这是本次唯一一处刻意的行为变更。

**统一到常量的位置**：`simulate_daily_dispatch` 默认参数、`_simulate_soc_for_rainflow`、`_joint_optimize_lp`。`optimal_dispatch_lp` 仍保留函数参数形式（由调用方传值）。

## 七半、算法链路巡检（6 套验证里的最后一套，30 项）

前面 5 套是「靶向验证」——只打改过的地方。这套 `sweep_algorithms3.py` 是「广度巡查」：拿一条真实生成的 30天×96点 曲线，把不依赖 UI 的核心函数逐个真调用一遍，看谁报错。

**它摇出两个真 bug，都不是前 29 条里有的**：

**P-30（时段格式三态不兼容）**：`_segment_periods` 只吃 `{'start':8,'end':11,'type':'flat'}` 这种 dict；但系统里同时存着两种别的写法——`PROVINCE_TARIFF_DB` 里是 `[(0,8,'valley'), ...]` 元组、外部导入常见 `('08:00','11:00','flat')` 字符串。传后两种进去必抛 TypeError。修法：新增 `_to_hour()` + `_normalize_periods()`，在 `_expand_overnight` / `_valid_periods` / `_segment_periods` 三个入口统一归一化。

实测三种格式：dict → 6 段、tuple → 6 段、'HH:MM' → 6 段，全部通过。

**P-31（MilpConfig 默认构造必崩）**：`devices=None` / `demands_price=None` 是 dataclass 默认值，而 `solve_milp_capacity` 直接做 `devices[j]` 下标和 `config.demands_price.get(...)`。用默认配置调用就是 `AttributeError: 'NoneType' object has no attribute 'get'`。修法：加 `__post_init__` 兜底为空容器。

实测：修前崩，修后返回正常 `MilpResult`。

**这套巡检还顺带证伪了 3 个我自己的错误猜测**：`simulate_daily_dispatch` 返回键是 `soc_trajectory`（不是 `soc`）；`periods_to_price_series` 返回双 Series 元组（不是单列表）；`solve_milp_capacity` 需要 `consume`/`produce`/`price`/`FiT` 四列（不是随便一个 df）。这三处都是测试写错，程序本身没问题——记在案例里，提醒自己以后先读签名再写断言。
