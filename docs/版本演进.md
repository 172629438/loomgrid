这个工具从 2026 年 5 月的 v1.1 走到今天的 v3.2，中间分叉成两条路线，又合并过一次。这段历史对使用者不重要，但如果你想在这里改代码，知道「为什么现在是这个样子」能省掉很多弯路。

## 两条路线

### Ultra（主线）

一路加功能，从 3 千行长到 3.5 万行。特点是**什么都有**：MILP、诊断、报告、批量、拟合、场景栈。

代价是单文件 96 个类，改一处要担心影响十处。

### Pro 融合版

2026 年 5 月从 v2.3 分叉出去，另起炉灶重写。不是裁剪 Ultra，是**用另一种架构实现同样的事**：

| 维度 | Ultra | Pro 融合版 |
|---|---|---|
| 行数 | ~35.8k | ~10.4k |
| 处理模式 | 全量加载后计算 | 流式 + 缓存 |
| 吞吐量 | 基准 | 约三成 |
| 调度策略 | 多引擎可选 | 单一最优路径 |
| 功能覆盖 | 全 | 核心 60% |

**融合版不是「Ultra 的精简版」，是另一种取舍**。它牺牲吞吐换来了架构清晰，适合理解主流程；Ultra 适合干活。

## 特性迁移史（重要）

这个项目最大的教训是：**特性会在版本迁移中静默丢失，而且没人发现**。

2026-10 做的一次全量审计发现：

### 丢失 1：v3.0 的三层叠加引擎

`_generate_load_profile`（省份基线 × 班制 × 设备 Markov × 噪声平滑）在 v3.2 里**完全不存在**。v3.2 只剩一个简化版 `generate_load_profile`（单层模板 × 月系数）。

连带丢失 6 个能力：`weekend_atten`、`cv`、`province`、`use_season`、`equipment`、`seed`。

已从 `备份程序.py`（v2.29+ 快照）原样回填 165 行。

### 丢失 2：350 行方法变成死代码

11 个方法（方案建议书、HTML 报告、结算明细、算法对比、循环分析、光伏导入、成本场景、自动诊断、设备对比等）被写在模块级函数 `fuse_load_curves` 的 `return` 之后。

语法合法，运行起来就是永不执行的嵌套函数。而 UI 层还在 `self._generate_proposal` 这样直接引用它们——意味着专业分析窗口在构建左面板时就该抛 AttributeError。

修法是把 350 行搬回 `ProfessionalWindow` 类体内，方法数 101 → 112。

### 丢失 3：18 个方法在参考程序里有、Ultra 里没有

用 AST 做四版本矩阵对照才发现。逐个核对后：

- **8 个是真功能**，已搬回（`register_simulated`、场景切换、策略导出、四目标优化、13 步诊断等）
- **10 个是占位壳**，拒绝搬（内部用 `× 0.85`、`容量 × 750` 这类常数冒充测算结果）

这个发现改变了项目的一条原则：**不是所有「旧版本有的东西」都值得补回来**。有些功能从来就没真正实现过，只是界面上有个按钮。

## 版本号错位的真相

目录结构与内部版本号严重不同步：

```
旧版本程序/
├── Pro 融合版 (v1.1)/   → 里面是 v1.1  ✓
├── Pro 融合版 (v1.2)/   → 里面是 v1.2  ✓
├── Pro 融合版 (v1.3)/   → 里面是 v1.3  ✓
├── Pro 融合版 (v1.4)/   → 里面是 v2.1  ✗
├── Pro 融合版 (v2.0)/   → 里面是 v2.0  ✓
├── Pro 融合版 (v2.1)/   → 里面是 v2.1  ✓
├── Pro 融合版 (v2.2)/   → 里面是 v3.0  ✗
└── Pro 融合版 (v2.3)/   → 里面写「智能增强版 v3.2」 ✗
```

原因：早期改名时把目录当「发布批次」用，而不是版本号。**判断版本要看文件头部的 `ULTRA_VERSION`，不要看文件名。**

## 给后来者的建议

如果你要接手改这个项目：

1. **先跑一遍 `algorithms/` 下的模块**，理解核心逻辑，别从 3.5 万行的主程序开始读。
2. **改任何测算相关代码前，先用同一组数据记录当前结果**。改完对照，不要凭感觉。
3. **不要相信注释里的版本标记**。`v3.2fix` 只能说明「这里被改过」，不能说明改对了。
4. **单文件是技术债，不是设计**。如果要做大改，先讨论拆分方案，别一个人闷头拆。
